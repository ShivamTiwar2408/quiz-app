Field guide · from the kernel out

Linux is one boundary,
and everything guarding it.

The video races through 100-plus terms. They're easier to hold if you see that almost all of them orbit a single line: the one between your software and your hardware. The kernel is that line. The shell, system calls, protection rings, users and permissions are all machinery for crossing it safely — or stopping you from crossing it at all. Learn the boundary first; the vocabulary falls into place around it.

§0 The one mental model

Picture your machine as concentric rings. At the dead center sits the hardware — CPU, RAM, disks, devices. Wrapped around it is the kernel, the only code allowed to touch that hardware directly. Around the kernel sits userspace: your shell, your editor, your browser, everything you actually run. A program in userspace cannot reach in and poke the hardware — it has to ask the kernel, through a narrow, guarded doorway called a system call.

Every concept in this guide lives somewhere on that map. Booting is how the innermost rings come alive. The filesystem, permissions, and users are rules the kernel enforces at the doorway. The shell and coreutils are the userland tools you use to send requests through it. Keep the picture in your head and the 100 terms stop being trivia — they become positions on a diagram.

The thesis: Linux protects the hardware behind the kernel and forces every program to request access through system calls. Understand that boundary and the rest is detail.

§1 Unix, POSIX & the lineage

To understand Linux you first meet its ancestor. Unix was an operating system built at AT&T Bell Labs in the 1970s. It was so influential that its ideas were codified into a standard — POSIX, the Portable Operating System Interface — so that different Unix-like systems would behave compatibly: same system-call shapes, same shell utilities, same conventions.

That standard is why skills transfer across systems. macOS, Android, FreeBSD, and most Linux distributions are POSIX-compliant to a large degree, which is why the same ls, cat, and pipe you learn here work almost everywhere.

Analogy: POSIX is to operating systems what a standard rail gauge is to railways — the trains (OSes) differ wildly, but because the track spacing is agreed, a lot of the same rolling stock runs on all of them.
Timeline: In 1987, MINIX — a small Unix-like OS for teaching — appeared, but its code couldn't be freely redistributed. That restriction inspired a Finnish CS student, Linus Torvalds, to write his own kernel in 1991: Linux.

§2 What "Linux" actually is

Here's the correction almost everyone needs: Linux is not an operating system — it's an operating-system kernel. It's written in the C language, and it's the layer that sits between your software and the hardware. On its own it boots and manages a machine, but it isn't the shell, the utilities, or the desktop — those come from elsewhere (see GNU).

It's also free and open-source software, licensed under the GPL 2.0. "Free" here means freedom, not price: you're free to run, study, modify, redistribute, and even sell it. That licensing is the reason Linux spread into everything from servers to phones to routers.

Kernel: the core program that manages memory, processes, the filesystem, and hardware, and mediates every request from userspace. When people say "Linux," they usually mean the kernel plus a stack of GNU tools and other software bundled around it — a distribution.

§3 The boot sequence

Pressing the power button kicks off a short, fixed relay race that ends at your login prompt. Each stage exists to bring the next inner-to-outer layer to life.

The bootloader (commonly GRUB) loads the kernel into RAM. The kernel detects hardware, then starts the init system — the first userspace process, typically systemd (alternatives exist). systemd brings up background services and then the login screen. From there, userspace programs run and you're in.

§4 What the kernel actually does

Once running, the kernel carries a lot of responsibility on behalf of every program. Four jobs matter most:

JobWhat it means
Memory managementAllocates and frees RAM for each process. Via virtual memory it can even hand out more memory than physically exists, by paging some to disk (swap).
Virtual filesystemA uniform way to read/write files regardless of the underlying disk format. The common default on Linux is ext4 (the fourth extended filesystem) — but it's one option among many.
Device driversTalks to peripherals — disks, GPUs, keyboards — through drivers, so programs don't need to know the hardware details.
Process schedulingDecides which process runs on the CPU and when (see Processes).
Analogy: virtual memory is a restaurant with 20 tables selling 60 reservations — it works because not everyone shows up at once. The kernel juggles who's actually "seated" in RAM versus parked on disk.

§5 Protection rings & system calls

You can't just walk up and poke the kernel, because the CPU enforces protection rings. Ring 0 is the kernel, with maximum privilege. Ring 3 is where the rest of us live in userspace, with the least. The rings are the hardware-level fence around that central boundary from §0.

So when a program needs something only the kernel can do — write a file, open a socket — it makes a system call, which briefly transitions the CPU from ring 3 to ring 0, does the privileged work, and drops back. In practice you rarely invoke a raw syscall yourself: you call a wrapper from glibc (the GNU C standard library), e.g. the write() function, which packages the real syscall for you.

hello.c — a syscall wrapper in action
// glibc's write() wraps the real "write" system call
write(1, "hello, kernel\n", 14);
//    ▲ fd=1 (stdout)   ▲ bytes    ▲ length
// ring 3 → [ syscall ] → ring 0 → pixels on screen → ring 3
Common mix-up: write in your C code is not itself the system call — it's a glibc wrapper. glibc provides wrappers for nearly every syscall, which is a big part of what makes the kernel usable from ordinary C.

§6 GNU & the coreutils

If the kernel is just the engine, what makes it a usable system? GNU (pronounced "guh-NOO", a recursive acronym for "GNU's Not Unix") — a project started by Richard Stallman in 1983, predating the Linux kernel itself. GNU supplies the coreutils: the everyday commands (ls, cat, echo, rm, and dozens more) that turn a bare kernel into something a human can operate.

Why some people say "GNU/Linux": a typical Linux system is the GNU userland running on top of the Linux kernel. Both halves are doing real work — the kernel manages hardware; GNU gives you the tools to command it.

§7 The shell & the terminal

The terminal is the graphical window that lets you type commands; the shell is the program inside it that interprets them. It's called a "shell" because it wraps a protective layer around the kernel — you talk to the shell, the shell arranges the syscalls. The most common shell is Bash.

Say hello with echo, a GNU utility that prints its argument to standard output. Under the hood, a syscall goes to the kernel, which checks permissions and drives the display — but as a user, you just see text.

bash
$ echo "hello, Linux kernel"
hello, Linux kernel

$ man touch          # pull up the manual for any command
TOUCH(1)   ... update timestamps / create an empty file ...
Your first reflex: when you don't know a command, ask man — the built-in manual. man touch, man ls, man man. It's the fastest way to learn without leaving the terminal.

§8 Working with files

A handful of coreutils cover most day-to-day file work. Note the split between a file's contents and its metadata (timestamps, size, ownership) — different commands read each.

CommandDoes
touch f.txtCreates a new empty file (or updates its timestamp if it exists).
lsLists files in the current directory.
cat f.txtPrints a file's contents (nothing shows for an empty file).
stat f.txtShows a file's metadata — birth, modified, and accessed times.
ls -lh-l = long details, -h = human-readable sizes. Flags combine: -lh.
rm f.txtRemoves a file.
Flags stack. Most single-letter flags can be merged behind one dash — ls -l -h and ls -lh are the same command, just more concise.

§9 Redirection & pipes

The real power of the terminal is combining commands. Two mechanisms do almost all of it: redirection moves a command's input/output to or from files, and pipes feed one command's output straight into the next.

OperatorMeaning
echo hi > f.txtRedirect output into a new file (overwrites it).
sort < f.txtRedirect a file in as a command's input.
a | bPipe — send the output of a as the input of b.

§10 Bash scripts

When you catch yourself running the same sequence over and over, put it in a Bash script — a file of commands you can run as one. You create it with a text editor: Vim or Emacs if you want the deep end, or nano, a minimal editor shipped with most distros, to just get it done.

The first line is a shebang (#!/bin/bash) telling Linux which interpreter to run the file with. After that, any Bash you like.

greet.sh
#!/bin/bash          # shebang: run this with bash
echo "What's your name?"
read name             # read a value from standard input
echo "Hello, $name"
Running it: save the file, then execute it by giving its path — e.g. ./greet.sh. (It needs execute permission first — see §14.)

§11 Users, root & sudo

Every account has a name (whoami) and a numeric UID (id). One account is special: root, UID 0 — the superuser/admin with maximum privilege.

  • su — switch to another user (root by default).
  • sudo <cmd> — run a single command with elevated privilege, if you've been granted it.
  • sudo -l — check what sudo privileges you currently have.

Linux also has groups, each with a group ID, which bundle users together so permissions can be managed for many people at once instead of one by one.

Respect UID 0. root can do anything, including destroy the system. Prefer sudo for the one command that needs it over living as root — a small habit that prevents large accidents.

§12 The filesystem hierarchy

Everything hangs off a single root, /. You start in your home directory (~), a personal workspace. Move around with mkdir (make a directory), cd (change directory), and pwd (print working directory). Run cd / and ls to see the top-level directories every Linux user should recognize:

When you type ls, Linux finds and runs an executable binary. Binaries live in /bin and /sbin, but also under /usr — and potentially anywhere. Which raises the question the next section answers: how does Linux know which binary to run?

§13 PATH & environment variables

PATH is a special environment variable holding a list of directories separated by colons. When you type a command, Linux searches those directories in order and runs the first matching binary it finds. That's the whole mechanism behind "how does the shell find ls."

You set environment variables with export. The common way to customize your PATH is to edit .bashrc — a script that runs before every terminal session, so your changes stick.

~/.bashrc
export PATH="$HOME/bin:$PATH"   # add your own bin dir, keep the rest
export PS1="\u@\h:\w\$ "         # customize the terminal prompt
PS1 is the environment variable that defines your prompt's look. Tweaking it (colors, username, path) is a popular bit of terminal vanity — and harmless practice with environment variables.

§14 File permissions

This is where the kernel enforces the boundary at the file level. Run ls -l and you'll see nine cryptic characters — the symbolic permissions. They're three triplets: owner, group, everyone else. Each triplet has read, write, execute — a letter means granted, a dash means denied.

CommandChanges
chmodPermissions — e.g. chmod 754 f or chmod o+r f (grant others read).
chownThe file's owner.
chgrpThe file's group.
Principle of least privilege: 777 lets everyone read, write, and execute a file — lucky on a slot machine, dangerous on a filesystem. Grant access only where genuinely needed, and trust no one by default.

§15 Processes & signals

Every command or program you run becomes a process on the CPU, managed by the kernel's scheduler. Each has a unique PID (process ID) and an owning user.

  • ps — list processes (PID + owner).
  • htop — an interactive, filterable process viewer.
  • daemons — system processes running quietly in the background (e.g. logging, networking).
  • ./long.sh & — append & to run your own process in the background.
  • crontab — schedule a script to run at set times (e.g. a 4:20pm daily reminder).

Sometimes a process misbehaves and must be stopped. You do that by sending it a signal:

CommandSignalEffect
kill <pid>SIGTERMPolitely asks the process to shut down — it can clean up first.
kill -9 <pid>SIGKILLForcefully terminates it immediately — no chance to clean up.
Reach for SIGTERM first. kill -9 is the sledgehammer — use it only when a graceful shutdown fails, since it gives the process no opportunity to save state or release resources.

§16 Utilities worth knowing

A few more standard tools show up constantly across Linux machines:

ToolPurpose
grepSearch through text for matching lines / patterns.
sedStream editor — find-and-modify text programmatically.
gzipCompress files to make them smaller.
tarArchive many files/directories into one (often paired with gzip).
tar vs gzip: they're often used together but do different jobs — tar bundles files into a single archive, gzip shrinks it. A .tar.gz is both applied in sequence.

§17 Distributions

Everything so far is roughly universal. Where Linux varies wildly is the distribution — a complete OS built on the kernel, with an opinionated bundle of default software for a target audience. Distros differ along a few axes:

AxisOptions
Package managerHow you install software — apt (Debian family), yum/dnf (Red Hat family), pacman (Arch).
Release modelFixed releases (predictable, stable) vs rolling releases (always cutting-edge).
Desktop environmentOn a PC, the GUI — GNOME, KDE Plasma, and others — shapes the whole feel.

Families worth knowing

FamilyKnown for
SlackwareThe original — one of the oldest distros, from the early '90s.
DebianThe most popular base overall; open philosophy, ease of use (Ubuntu descends from it).
Red HatThe enterprise choice, valued for long-term support.
ArchMinimal, rolling, build-it-yourself. Home of the "I use Arch, by the way" ethos.
Analogy: the kernel is the engine; a distro is the finished car. Same engine can sit in a family sedan (Ubuntu), a work truck (Red Hat), or a stripped-down track build you assemble yourself (Arch).
