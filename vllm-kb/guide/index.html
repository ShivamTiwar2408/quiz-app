Part 0 — Why this was built

What the vLLM creators saw missing in 2022

vLLM came out of UC Berkeley's Sky Computing Lab in 2023. To understand what they fixed, you have to see what serving LLMs looked like just before — and why it frustrated everyone trying to run these models affordably.

The landscape before vLLM

how people served LLMs before continuous batching + paging
naïve / static batching
Group a few requests, run them, and wait for the slowest to finish before taking new ones. Short requests sit idle holding their slot. The GPU spends much of its time half-empty.
FasterTransformer
NVIDIA's highly-optimized kernels — fast at the math, but still static batching and contiguous, reserve-the-max KV memory. Great single-request latency, poor throughput under real mixed traffic.
HF TGI
HuggingFace's Text Generation Inference — a production server that made deployment easy, but (at the time) inherited the same contiguous-KV memory waste.
Orca (2022)
The research breakthrough just before vLLM: it introduced continuous batching (swap requests in and out every step). A huge scheduling win — but it still stored each request's KV cache as one contiguous, reserve-the-max slab.

The gap they spotted

The Berkeley team profiled these systems and found the real bottleneck wasn't compute — it was wasted GPU memory. Existing engines were squandering 60–80% of the KV cache memory to fragmentation and over-reservation (the problems we'll dissect in Part 4). Less memory used well = more requests in parallel = higher throughput. Orca had fixed scheduling; nobody had fixed memory.

💡 The insight that started the projectMemory was being managed the way 1950s programs managed RAM — one big contiguous block per process. Operating systems had already solved that decades ago with virtual memory and paging. "What if we applied paging to the KV cache?" That question became PagedAttention, and pairing it with Orca-style continuous batching became vLLM — reported at up to 24× the throughput of HF Transformers and well above TGI/Orca on the original benchmarks.

So this guide builds up in exactly that order: first the fundamentals (tokens, KV cache), then the memory problem, then the two ideas that fixed it — and finally the extras (multi-LoRA, speculative decoding, scaling) that turned a research prototype into the most widely-used open inference engine. Let's start at the bottom.

Part 1 — The foundation

What an LLM actually does: predict the next word

A Large Language Model (LLM) — the thing behind ChatGPT, Claude, Gemini — has exactly one core skill: given some text, guess what comes next. That's it. Everything else is that one trick repeated very fast.

Step A — your words become tokens

Computers don't read English. So your sentence is chopped into small pieces called tokens (roughly word-fragments), and each token is swapped for a number — an ID — from the model's dictionary. This is tokenization.

tokenization
Hi, my name is
↓ tokenizer ↓
154111242756298

From here on, the model only ever sees numbers. A token's size in memory has nothing to do with how long the word is — "a" and "antidisestablishmentarianism" each become one (or a few) IDs.

The vocabulary — the model's fixed alphabet

That "dictionary" has a proper name: the vocabulary. It's a fixed, finite set of known tokens — every model is built around its own. Any text you ever type is expressed only as combinations of these pieces; there's nothing outside the vocab. The number of tokens a model knows is its vocabulary size, and it varies a lot by model:

vocabulary size by model (approx.)
ModelVocab size (≈)
GPT-250,257
Llama 2 / TinyLlama32,000
Llama 3.x128,256
GPT-4o~200,000
Gemma~256,000

Bigger vocab = each token carries more meaning (fewer pieces per sentence), but a longer list to score every step. Hold onto this number — it comes back twice: it's the length of the probability list the model produces each step (next), and the size of the mask used in guided decoding (Part 8).

Step B — it generates one token at a time

The model reads all your tokens, then produces a probability score for every token in the vocabulary — "how likely is each one to come next?" It picks a token from that list (usually sampling rather than always taking the top one — see below), appends it to the text, and repeats — reading everything again to score the next one. This loop is called autoregression, and it stops when the model emits a special "I'm done" (end-of-sequence) token.

🎲 Why the same prompt gives different answersThe model doesn't always take the single most likely token — it samples from the probability list. Temperature controls how adventurous that pick is (higher = more random), and top-p limits sampling to the most probable tokens that together cover, say, 95% of the probability. That controlled randomness is why ChatGPT rarely repeats itself word-for-word.

autoregressive generation
prompt: 5 tokens

Notice the catch: to make each new token, the model re-reads the entire growing sequence. By token #500 it's re-reading 500 tokens every single step. That waste is exactly what vLLM is built to fix.

🧠 Mental modelAn LLM is an extremely well-read autocomplete. It doesn't "think ahead" — it commits to one token, then reconsiders everything to pick the next.
Part 2 — Why this is expensive

Everything happens on a GPU, and GPU memory is tiny & pricey

LLMs run on GPUs — specialized chips that do massive math in parallel. The scarce resource isn't speed, it's VRAM (the GPU's onboard memory). A model's whole world has to fit in VRAM, and VRAM is small and expensive.

How a GPU's memory gets divided up

Picture the VRAM as a plot of land. Several tenants must share it. Example: one NVIDIA A100 with 40 GB holding a 13-billion-parameter model.

The model weights and overhead are fixed. The only space we can manage cleverly is the KV cache — and how well we use it decides how many users we can serve at once.

Where does ~26 GB come from? Each parameter needs memory: at 2 bytes each (FP16, the common half-precision format), a 13-billion-parameter model = 13B × 2 ≈ 26 GB, before anything else loads.

💸 Why you should careBetter memory management = more users per GPU = lower cost per answer. That single sentence is the entire business case for vLLM.
Part 3 — The clever shortcut

The KV cache: don't redo work you've already done

Remember the waste from Part 1 — re-reading the whole sequence for every new token? To predict the next token, the model uses attention: each token "looks back" at earlier tokens to decide which ones matter. For that, each token is turned into three vectors — a Query (Q) ("what I'm looking for"), a Key (K) ("what I'm about"), and a Value (V) ("the information I carry"). A token's Query is compared against every earlier token's Key to score relevance, and those scores blend the Values together. That's attention in one sentence.

Attention, step by step — the Q·K → softmax → V recipe

Let's make that one sentence concrete, because these four steps are the attention mechanism (the famous "scaled dot-product attention"). Say the current token wants to look back over the sequence:

scaled dot-product attention for one token

In one line: Attention(Q,K,V) = softmax(Q·Kᵀ / √d_k) · V

The output — the context vector — is a custom blend of the earlier tokens' Values, weighted toward whichever ones this token found most relevant. It's the token "having read the context." A few details that round out the picture:

  • Scaling by √d_k (step ②) stops the dot-products from getting huge as vectors get longer, which would make softmax too "spiky" and kill the gradient signal.
  • Causal masking — a token may only attend to tokens before it (future scores are set to −∞ before softmax). This is what makes the k/v cacheable, as we'll see.
  • Multi-head — this whole recipe runs in parallel across many "heads," each with its own Q/K/V projections, so the model can attend to several kinds of relationship at once; the heads' context vectors are concatenated.
  • After attention, the context vector flows through the rest of the transformer layer (a feed-forward network, plus residual connections and layer normalization that keep values in a stable range), and the stack of layers ultimately produces the next-token probabilities from Part 1.
🔑 Why this section matters for vLLMEvery term here comes back: K and V are what the KV cache stores; Q is what it doesn't (next); the Q·Kᵀ score matrix is the giant intermediate FlashAttention avoids materializing (Part 5); and softmax over scores is exactly what guided decoding's bitmask edits (Part 8).

Where do Q, K, V come from? Two ingredients — one frozen, one fresh

This is the crux, so let's be exact. A token's vectors are computed by multiplying that token's representation by three projection matrices: q = x·WQ, k = x·WK, v = x·WV.

training vs inference — what's fixed, what's computed

🧊 Learned in training → then FROZEN

The weight matrices WQ, WK, WV (and the output WO) are what training actually tunes. Once training ends they never change — they ship inside the model weights (that ~26 GB from Part 2). vLLM is an inference engine, so for everything we discuss, these matrices are read-only constants.

🔥 Computed fresh at inference → per token

The actual q, k, v vectors are produced at run time — one set per token — by multiplying that token's hidden state by the frozen matrices. New tokens ⇒ new vectors. These are computed, not learned.

So when people say "compute K and V," they mean the k and v vectors for each token — produced on the fly from the frozen WK, WV. The matrices are fixed; the per-token vectors are what's new each step.

Now the key insight that makes caching possible: thanks to causal attention (a token can only look at tokens before it, never after), an earlier token's k and v vectors don't depend on any later token. So once a token's k and v are computed, they're final — they never change. (Its Query, by contrast, is only needed in the step that token is generated, so it isn't worth caching.)

So the trick is obvious in hindsight: compute each token's k and v vectors once, then save them. That saved store is the KV cache — it holds the computed k and v vectors, not the W matrices (those already live in the model weights). Generating a new token then only computes k/v for that one new token and reuses every cached vector.

⚠️ Common confusion, cleared upThe KV cache does not store WK/WV — those are frozen weights, shared by every token and every request. The cache stores the output of applying them: the per-token k and v vectors. That's why cache size grows with the number of tokens (and users), while the weights stay a fixed cost.
Go deeper: why cache K and V but not Q?

This is the question that explains the name — it's the KV cache, not the QKV cache. Let's watch one decode step to see why.

Say the model has already generated tokens 0…t−1 and is now producing token t. It computes just one new query, qt, for the current position. Attention for this step is:

scores = qt · [k0, k1, …, kt]ᵀ → softmax → weighted sum of [v0, v1, …, vt]

Look closely at how each vector gets used over the whole generation — that's where the asymmetry lives:

  • Every old token's k and v are read again at every future step. Token 3's k and v are needed when generating token 4, 5, 6, … forever after. Reused many times ⇒ caching them saves enormous recompute.
  • A token's query qt is used in exactly one step — the step that generates token t. It's compared against the earlier keys, the token is produced, and then qt is never needed again. Because of causal masking, no later token ever "looks back" using an old query — later tokens look back with their own queries. Used once ⇒ caching it would just waste memory.

So the rule falls out of the math: K and V are the "looked-at" side (read by many future queries → cache them); Q is the "looking" side (one position's momentary question → discard it after use). That asymmetry is exactly why it's called the KV cache.

Every step recomputes K/V for all tokens. Step 500 = 500 tokens of work.

✅ With KV cache

Two phases fall out of this: prefill & decode

⚡ Prefill

Process all your prompt tokens at once to fill the KV cache and produce the first new token. Lots of math in parallel → compute-bound (limited by raw GPU horsepower).

🔁 Decode

Generate the rest, one token per step, reusing the cache. Little math, lots of memory shuffling → memory-bandwidth-bound (limited by how fast you can read memory).

🍳 AnalogyPrefill is prepping every ingredient before you start cooking (big upfront burst). Decode is plating one dish at a time, reusing the prep. Different bottlenecks — remember this; it explains almost every vLLM design choice later.
Part 4 — The problem vLLM was born to solve

The old way wasted most of the memory

We now know what the KV cache is. The question that made vLLM famous is how to store it — because the way everyone did it before turned out to waste most of the GPU's expensive memory. To see why, we have to look under the hood of the older engines first.

First, how the old way actually worked

Let's be concrete, because the waste only makes sense once you see the mechanism. Older serving systems (e.g. FasterTransformer, HuggingFace TGI, and the research system Orca) all stored each request's KV cache as one contiguous slab — a single unbroken stretch of VRAM. There was no paging: the slab had to be one continuous piece.

What's stored in that slab? Not your prompt text, and not the answer text. It holds the k and v vectors for every token processed so far — your prompt tokens (written during prefill) plus each token generated after. It grows by one token's worth every decode step.

How big a slab does a request get? Here's the costly decision: the system reserved the slab up front, sized for max_model_len — the largest answer the request could ever produce (say 2,048 tokens) — because the slab can't grow into its neighbors later (it must stay contiguous). So it grabbed the worst case immediately, on arrival.

What if a request needed more than its slab? It can't — the slab is the maximum, so it never runs out mid-answer. That's the whole point of over-reserving… and exactly why it bleeds memory: nearly every request reserves far more than it uses.

With a fixed 12 GB KV budget and a 256 MB slab per request (2,048 tokens × 128 KB), the math is brutal: 12 GB ÷ 256 MB ≈ 48 requests max — and in practice ~40 once other overheads are counted — on a GPU that could serve hundreds. Two distinct wastes fall out of this:

Villain ①: internal fragmentation

Waste inside a slab you were already given. You reserved 256 MB but the answer was short — so most of your own block sits empty. It's "internal" because the wasted space is locked inside an allocation that belongs to one request.

internal fragmentation — waste INSIDE one request's slab

A request reserves room for 2,048 tokens (256 MB) but only generates 100 tokens (12.5 MB):

used 12.5 MB
wasted 243.5 MB — still reserved by this one request 😱

The 243.5 MB isn't free for anyone else — it belongs to a request that simply isn't using it.

Villain ②: external fragmentation

Some systems tried to be clever and guessed smaller sizes per task type (chatbot=500, code=2,048, summary=1,000 tokens). That created a different waste: free gaps between requests that are individually too small to fit a new arrival — even though their total is plenty. It's "external" because the wasted space sits outside every allocation, in the gaps between them.

external fragmentation — waste in the gaps BETWEEN slabs

1,500 tokens free in total, but a request needing 1,200 contiguous tokens → out-of-memory error, because neither gap is big enough alone. The space exists; it's just in the wrong shape.

🅿️ The names, made obviousThink of a parking lot. Internal = you rented a whole bus bay for your bicycle — wasted space within your own spot. External = there are three single gaps scattered around, but a delivery truck needs three adjacent spots and can't fit — wasted space between others' spots.

Villain ③: no sharing

Ask for "3 alternative answers" and the old way stored your prompt's KV three times — identical copies — because each answer lived in its own separate contiguous slab. Wasteful, since the prompt's k/v vectors never change.

🎯 The three villainsInternal fragmentation (over-reserving inside a slab), external fragmentation (unusable gaps between slabs), and no memory sharing. All three trace back to one root cause: contiguous, reserve-the-maximum allocation. The next section kills the root cause with one idea borrowed from operating systems.
Part 5 — The big idea

PagedAttention: steal the trick your laptop already uses

Your operating system solved this exact problem decades ago. Programs think they have one long continuous block of memory, but the OS secretly scatters it across small fixed-size pages in physical RAM, and a page table remembers where each page really lives.

how OS virtual memory paging works
📖 The mapping (memorize this line)vLLM applies that exact trick to the KV cache: blocks are pages · tokens are bytes · a request is a process. The one difference: the OS uses a hardware chip (the MMU) for the lookup, while vLLM does it in software (the Block Manager). Everything else follows from this analogy.

KV memory is chopped into small fixed-size blocks

Instead of one giant reservation, the KV cache is split into many small blocks (16 tokens each, by default). A request grabs only as many blocks as it needs — and they can sit anywhere in physical VRAM. A lightweight page table (called the Block Manager) maps the request's neat logical order to the scattered physical blocks.

a request's logical blocks → its block table → scattered physical VRAM

No giant contiguous reservation needed → external fragmentation gone. Blocks are tiny, so a near-empty last block wastes ≤15 tokens → internal fragmentation almost gone.

⚙️ Why it's called paged attention, not just paged memoryScattering KV across blocks creates a problem: the attention step (Part 3) needs to read all of a sequence's Keys and Values, but now they're spread all over VRAM. So the attention kernel (GPU code) must follow the page table and read straight from the scattered blocks — no gathering them into one place first. That paged-aware kernel is the actual "PagedAttention"; the block bookkeeping is only half the idea.

Where FlashAttention fits in

A natural question: isn't FlashAttention the famous fast-attention trick? Yes — and it's a core part of vLLM. But it's not a competitor to PagedAttention; they compose, each solving a different problem.

FlashAttention vs PagedAttention — different jobs, used together

⚡ FlashAttention — the math

A kernel that computes attention without ever writing the giant N×N attention matrix to memory. It streams over the K/V in tiles, keeping running softmax stats on-chip (in fast SRAM). Result: far less memory traffic and no quadratic memory blow-up — the speed of each attention step.

📄 PagedAttention — the layout

Decides where the K/V live — scattered 16-token blocks plus a page table — so memory isn't wasted (Part 4). It doesn't compute attention; it organizes the data the attention kernel reads.

vLLM's FlashAttention backend is paged-aware: it does FlashAttention's tiled math, but instead of reading one contiguous K/V buffer it follows each request's block table to gather tiles from the scattered blocks. So you get FlashAttention's speed and PagedAttention's memory efficiency in one kernel.

Why SRAM matters: the GPU memory hierarchy

FlashAttention's whole trick rests on one hardware fact: a GPU has several kinds of memory, and they differ in speed by orders of magnitude. The faster a memory, the tinier and closer-to-the-cores it is. Here's the hierarchy (figures for an A100):

GPU memory hierarchy — small+fast at top, big+slow at bottom

The gap that matters: SRAM is ~10× faster than HBM but ~1000× smaller. The cores can only do math on data sitting in registers/SRAM — anything in HBM must be hauled in first, and that hauling is the real cost.

💡 Why this makes FlashAttention a huge winNaïve attention writes the full N×N score matrix out to HBM, then reads it back to do softmax, then reads it again to weight the values — three slow round-trips over the big-but-slow memory, and the matrix itself grows quadratically with sequence length. FlashAttention instead loads K/V tiles into SRAM, computes scores + a running softmax + the weighted sum entirely on-chip, and only writes the final result back to HBM. The giant matrix never touches HBM. Since attention is memory-bound (bottlenecked by HBM traffic, not arithmetic — Part 10's roofline), cutting HBM round-trips is exactly what makes it faster and lets it handle long sequences without running out of memory.
🔗 How it ties back to vLLMThis is the same memory story from Part 2, one level deeper. vLLM fights to fit more in HBM (PagedAttention) and to keep the cores fed (continuous batching); FlashAttention fights to keep attention's working set in SRAM. Both are attacking the same enemy — HBM bandwidth — from different angles, which is why they pair so naturally.
🔌 The attention layer is pluggable"FlashAttention" is one of several interchangeable attention backends vLLM picks at startup (the "set the backend to FlashAttention" step from the worker init). The registry includes FLASH_ATTN (the default on most NVIDIA GPUs), FLASHINFER, TRITON_ATTN, and specialized MLA backends like FLASHMLA (for models such as DeepSeek). You can override it with --attention-backend FLASH_ATTN. They all consume the same paged KV blocks — the backend is just how the attention math runs on the hardware.

Sharing is now free: ref-counts

Three answers to the same prompt? They simply point to the same prompt blocks. vLLM keeps a reference count (ref_cnt) per block — "how many requests use me." Shared prompt blocks just bump the count instead of copying. Memory sharing → solved too.

How this compares to the engine just before it: Orca

It helps to measure the jump against a real predecessor. Orca (2022) was the state-of-the-art research engine right before vLLM, and it introduced the big scheduling win — iteration-level (continuous) batching, which we cover next. But Orca still stored each request's KV in a contiguous, reserve-the-max slab — so it kept the fragmentation problems from Part 4.

Go deeper: how big is one block, really?

One block stores the k and v vectors for block_size tokens, across every layer's attention heads. The size formula:

block_bytes = 2 (K&V) × block_size × num_kv_heads × head_dim × bytes_per_element

For Llama-3 8B in FP16, one token costs ~128 KB, so a default 16-token block ≈ 2 MB. If 8 GB of VRAM is left for KV cache, that's ~4,096 blocks to hand out. vLLM computes this number at startup and prints it as the available "GPU blocks."

What actually happens when vLLM starts up on a GPU

Concretely, when you launch vLLM on a GPU it does a one-time setup, in this order — and the numbers it prints come straight from the ideas above:

vLLM startup sequence
1
Load model weights into VRAM. The frozen W matrices (incl. WK/WV) land on the GPU — e.g. ~16 GB for Llama-3 8B in FP16.
2
Run a profiling pass. vLLM does one dummy forward pass to measure peak activation/working memory the model needs to run.
3
Claim the leftover for KV cache. Whatever VRAM remains — up to a configurable fraction gpu_memory_utilization (≈0.9 by default) — is carved into fixed-size blocks. vLLM prints e.g. # GPU blocks: 4096.
4
Reserve a few CPU blocks too (# CPU blocks) as overflow swap space — used to temporarily offload a request's KV to system RAM under pressure, then bring it back.
⚠️ What vLLM does and doesn't claim at load timeNotice every step above is about memory — weights, activations, KV blocks. vLLM never allocates CUDA cores. That's the single most common misconception, so let's be exact about what the cores even are.

So how many CUDA cores does the model get?

Short answer: all of them, all the time — because cores aren't allocated. A GPU's compute units are fixed silicon, shared dynamically across whatever work is running. When the model loads, vLLM claims a slice of VRAM (the memory); the cores are just the engine the kernels run on — they aren't reserved, partitioned, or "given" to the model.

fixed compute (not allocated) vs allocated memory — NVIDIA A100 / H100

When a kernel runs (say the PagedAttention kernel), the GPU's scheduler hands its threads to whatever cores are free at that instant — across all 6,912 (A100) or 16,896 (H100) of them. Two requests in the same batch share the same cores in the same launch. There's no per-model core budget to set.

💡 Why vLLM obsesses over memory, not coresThis is the deeper reason the whole engine is built around the KV cache. During decode you compute one token at a time — that barely uses the thousands of cores, but it must stream all the weights + KV through memory. So decode is memory-bandwidth-bound, not core-bound (the roofline, Part 10). The cores sit largely idle; the bottleneck is memory. That's exactly why vLLM spends its cleverness on fitting more in VRAM and batching (to feed those idle cores) rather than on the cores themselves.
🧩 And the "blocks" name clashKV blocks are memory — slots of VRAM holding k/v vectors. CUDA thread blocks are compute — groups of threads a kernel launches onto the cores above. Same word, unrelated things: one is where data lives, the other is how a kernel's work is scheduled onto the fixed cores. vLLM's innovation is almost entirely about the memory kind.
Quick check: why are blocks made small (16 tokens) instead of huge?
Right idea: a small block means the only waste is in the final partly-filled block (≤15 tokens), and tiny blocks slot into any free gap — killing both kinds of fragmentation.
Part 6 — Serving many people at once

Continuous batching: never let the GPU sit idle

First — what is a batch, and why bother?

📖 Definitions (verbatim, authoritative)Batch — "The set of examples used in one training iteration." Batch size — "The number of examples in a batch." — Google Machine Learning Glossary. (In our serving case, an "example" is one request being processed in a step.)

A batch is simply a group of requests the GPU processes together, in one pass, instead of one at a time. Why does that help? A GPU has thousands of tiny math cores. Running a single request leaves almost all of them idle — like driving a 50-seat bus with one passenger. Batching fills the seats.

📖 What's a "pass"? — the forward passThat "one pass" through the model is the forward pass: the system "processes a batch of examples to yield prediction(s)" (Google ML Glossary). In code it's just calling the model on the input — which "executes the model's forward, along with some background operations" (PyTorch docs). For an LLM, one forward pass turns the current tokens into the next-token probabilities. The whole batch goes through together in that single pass — that's why batching is efficient.
why batch? one request barely uses the GPU
1 request at a time

~5% of cores busy. You pay for the whole GPU, use a sliver.

vs
A batch of requests

Practical example: 4 users ask questions in the same second. Process them one-by-one and each waits for the previous to finish. Put all 4 in a batch and the GPU answers them together in roughly the time it took to do one — because the bottleneck was loading the model weights from memory, which all 4 now share.

So batching is essential. The only question is how you batch — and that's where vLLM beats the old approach.

The old static batching locked a batch at the start: gather N requests, run them together, and wait for the entire batch to finish before admitting anyone new. Since requests finish at wildly different lengths, the short ones sit idle holding their slot while the longest one drags on.

That inner triangle — Scheduler → Model Executor → back through the KV Cache Manager — is the step loop, the heartbeat of vLLM. Calling generate() just spins this loop: schedule (pick requests + blocks) → forward pass (GPU predicts the next tokens) → postprocess (collect tokens, free finished requests), over and over until every request is done. Prefill and every decode step are each one trip around it.

Inside the system design: the real components

Let's go one level deeper than boxes — this is the actual internal design of vLLM's V1 engine. At the top sit two entry classes: LLMEngine (synchronous, for offline batch use) and AsyncLLMEngine (async, used by the OpenAI-compatible server). Both wrap the same EngineCore, which holds the parts that do the work. Expand each card for the real class names you'll meet in the codebase.

The 4 wrapper components (input → core → output)

A request passes through four layers around the core:

  • vLLM config — every knob: model, cache, parallelism (TP/PP/DP), dtype. Built once at startup and threaded everywhere.
  • Processor — validates the raw input, tokenizes it, and turns it into an EngineCoreRequest (carrying prompt_token_ids, sampling params, priority, arrival time).
  • EngineCore client — the handle the outside world uses to talk to the core. In simple offline use it's an InprocClient (literally the core in the same process); at scale it becomes a multiprocess client (DPLBAsyncMPClient) that talks over ZMQ sockets.
  • Output processor — converts the core's raw EngineCoreOutputs back into the RequestOutput the user sees (detokenized text, finish reason).
Inside EngineCore: executor · scheduler · KV manager · structured-output

The EngineCore itself is made of:

  • Model Executor — drives the forward passes. On one GPU it's a UniProcExecutor (a single Worker); on many GPUs it's a MultiProcExecutor (one Worker process per GPU). The Worker owns a model_runner (sampler, KV cache, forward-pass buffers) and an InputBatch (CPU-side buffers + the per-request block tables).
  • Scheduler — decides which requests run in the next step. Has a policy (FCFS or priority), a waiting queue and a running queue.
  • KV Cache Manager — the heart of paged attention. Maintains the free_block_queue — a doubly-linked pool of free KV blocks (often hundreds of thousands) — and req_to_blocks, mapping each request to its allocated blocks (its page table).
  • Structured Output Manager — drives guided decoding (grammar bitmasks; Part 8).
Startup: the 3 things each GPU Worker does before serving

When the executor builds a Worker, three procedures run (and later run independently on every GPU under MultiProcExecutor):

  • ① Init device — pin a CUDA device, check dtype support, verify VRAM against gpu_memory_utilization, set up the distributed groups (DP/TP/PP/EP), and create the model_runner + InputBatch.
  • ② Load model — build the architecture, load the weights, call model.eval(), and optionally torch.compile().
  • ③ Initialize KV cache — get the per-layer KV spec, run a profiling forward pass + GPU memory snapshot to compute how many blocks fit, allocate & bind the KV tensors to the attention layers, and — unless --enforce-eager — capture CUDA graphs (pre-recorded GPU work replayed each step to cut kernel-launch overhead).
One step() in detail: schedule → forward → postprocess

Each turn of the loop has three stages (V1 can mix prefill and decode in the same step — V0 could only do one type at a time):

  • ① Schedule. Decode requests go first (they're in the running queue). For each, compute how many new tokens (usually 1, more with speculative/async), call allocate_slots, and subtract from the token budget. Then admit prefill requests from the waiting queue until the budget runs out, moving each WAITING → RUNNING.
  • ② Forward pass. The flattened batch runs through the model; the sampler picks one token per sequence (honoring temperature/top-p, and the grammar bitmask if guided).
  • ③ Postprocess. Append each sampled token to its Request, detokenize, and check stop conditions (length limit, EOS id, stop_token_ids, or stop strings). A finished request is cleaned up — its KV blocks return to the free_block_queue — and its output is returned (streamed, token-by-token, in serving mode).
allocate_slots: how the KV manager hands out memory

The scheduler leans on allocate_slots every step. It:

  • Computes block count — n = ceil(new_tokens / 16) (16 = default block size). 17 new tokens → 2 blocks.
  • Checks availability — if the pool can't supply n blocks, it may trigger recompute preemption: evict a low-priority request (freeing its blocks back to the pool, to be recomputed later) or skip scheduling this step.
  • Allocates — pop the first n blocks off the free_block_queue and record them in req_to_blocks[request_id]. With prefix caching on, already-computed blocks are reused first (Part 8).

This is the exact moment the "page table" from Part 5 gets written — logical block → physical block id.

🏷️ V0 vs V1Everything above describes the V1 engine (the current default; V0 is deprecated). The headline V1 wins: it can mix prefill + decode in one step, and it splits work across separate processes communicating over ZMQ — per the official architecture docs, a single-node tp=4 deploy runs 6 processes (1 API server + 1 engine core + 4 GPU workers), and the engine-core count scales to 1 per data-parallel rank (+ a DP coordinator when DP>1). Splitting the API server from the engine means tokenization/HTTP never block the GPU loop. Class names may shift release-to-release — the roles are what matter.

Where does vLLM actually run?

Those boxes are the engine's logical parts. So what is a running vLLM, physically? It's a Python process on a host machine that drives one or more GPUs. The CPU side does the orchestration (HTTP API, tokenizing, the scheduler, the block manager / page table); the GPU side holds the model weights + KV cache and runs the math kernels. It's almost always packaged as a Docker container — the official image is vllm/vllm-openai, exposing an OpenAI-compatible API on port 8000.

one vLLM deployment on one node (TP = 4 example)

How many processes & containers? In V1, the API server and the engine core are separate processes talking over ZMQ — so HTTP/tokenization never blocks the GPU loop. A tp=4 single-node deploy = 6 processes: 1 API server + 1 engine core + 4 GPU workers (one per GPU). All inside one container per node — you don't run one container per GPU. For more traffic, add replicas (more containers/nodes) behind a load balancer — that's data parallelism (Part 9), which adds 1 engine core per DP rank and a DP coordinator process.

Part 8 — The clever extras

Six upgrades that make it even better

Everything so far is the core. These features bolt on top. You don't need all the details — just the why behind each. Expand any card.

① Chunked prefill — don't let one long prompt hog the GPU

A 10,000-token prompt would monopolize a step and stall everyone else's decoding. Solution: split a long prompt into fixed-size chunks and prefill it across several steps, letting quick decodes interleave. Smoother for everyone — no single request blocks the line.

② Prefix caching — reuse work across different requests

If many requests share the same opening text (a long system prompt, a document), why recompute its KV every time? vLLM hashes each completed block of tokens (chaining in the previous block's hash, so the hash captures the whole prefix). A new request with the same prefix finds the hash, reuses those cached blocks (ref_cnt++), and skips straight to the new part. Huge win for chatbots and RAG.

③ Guided decoding — force valid output (e.g. always valid JSON)

Need the model to only ever output "Positive" or "Negative", or strict JSON? A finite state machine (a grammar) tracks which tokens are legal next. At each step, illegal tokens have their score set to -infinity via a bitmask — so they can never be picked. The model is gently railroaded into valid output.

④ Speculative decoding — guess ahead, verify in bulk

Decode is slow because it's one token at a time. Trick: a tiny, fast "draft" model guesses the next k tokens. The big model then checks all k guesses in a single pass. Correct guesses are kept for free; the first wrong one is rejected and corrected. Rejection sampling guarantees the output is identical to what the big model would have produced alone — just faster. vLLM supports n-gram, EAGLE, and Medusa style proposers.

⑤ Disaggregated P/D — put prefill and decode on different GPUs

Recall: prefill is compute-bound, decode is memory-bound — opposite appetites. So run them on separate machines, each tuned for its job. The prefill GPU computes the KV cache, then ships it over a fast connector (e.g. NIXL) to the decode GPU, which generates the answer. Each side scales independently.

⑥ Multi-LoRA serving — many fine-tuned models, one GPU

The problem. A LoRA adapter is a tiny "diff" (often just tens of MB) that fine-tunes a big base model for a specific task — a support bot, a coding helper, a legal summarizer. If you have 100 such fine-tunes, the naïve way is 100 separate deployments — 100 copies of the multi-GB base model loaded on 100 GPUs. Absurdly wasteful, since they all share the same base.

vLLM's fix. Load the base model once, and keep each LoRA adapter as a small add-on in memory. Then — the clever part — requests for different adapters are served in the same batch: every token still flows through the shared base weights, and each request's own little adapter is applied on top. Specialized GPU kernels (vLLM's Punica / SGMV kernels) do this mixed-adapter math efficiently in one pass, so mixing adapters adds minimal overhead.

The payoff: serve dozens-to-hundreds of fine-tuned variants from a single base-model deployment. Enabled with --enable-lora; tuned with max_loras (how many distinct adapters per batch), max_lora_rank, and max_cpu_loras (how many to keep parked in CPU RAM, swapped to GPU on demand — paging again!).

Part 9 — When one GPU isn't enough

Scaling to many GPUs & many machines

We just saw that one vLLM deployment is a single container driving its GPU(s). Now: how do you grow beyond one node — for a model too big to fit, or traffic too big for one copy? Big models don't fit on one GPU, and big traffic needs many copies. Three axes:

Tensor Parallelism (TP)

Split each layer's math across several GPUs in one machine. A driver broadcasts the work; all GPUs compute their shard together. Preferred inside a machine because GPUs there share fast links.

Pipeline Parallelism (PP)

Put different layers on different machines, like an assembly line. Used to span across machines when one box can't hold the model.

Data Parallelism (DP)

Run several full copies (replicas) of the engine; a coordinator load-balances users across them. This is how you serve more traffic.

Headless + API node

One node runs the public API server; other "headless" nodes just run engine replicas behind it. Clients only ever see the API node.

🏭 AnalogyTP = many workers building one car together. PP = an assembly line passing the car down. DP = many identical factories. Real deployments mix all three.
Part 10 — Measuring "fast"

Latency vs throughput, and the roofline

"Fast" means two different things, often in tension:

⏱️ Latency (one user's happiness)

TTFT — time to first token (how long until you see anything; set by prefill).

ITL / TPOT — time between tokens (how fast it "types"; set by decode).

E2E — total time for the full answer.

📊 Throughput (the operator's wallet)

Total tokens/second across all users. Bigger batches = more throughput, but each individual user may wait a touch longer. Goodput = throughput that still meets your latency promises.

The roofline: why bigger batches help — up to a point

This is the one chart that ties it together. The hill has two slopes: a rising "memory" wall and a flat "compute" ceiling.

roofline model
Decode sits on the blue slope — starved for memory bandwidth.

On the blue slope you're memory-bound (typical of decode) — the GPU's math units sit idle waiting for data. Pack more requests together (continuous batching!) and you climb right toward the red ceiling, finally using the GPU fully. That's why batching is the heart of vLLM.

The whole story in one breath

You now understand vLLM

An LLM predicts one token at a time, re-reading everything each step. To avoid that waste it saves each token's Key/Value in the KV cache. That cache is precious GPU memory, and the old way of storing it in big contiguous chunks wasted most of it (internal + external fragmentation) and couldn't share.

vLLM borrows the operating-system idea of paging: chop KV memory into small blocks, map them with a page table, and reference-count for sharing — that's PagedAttention. On top, continuous batching keeps the GPU busy by swapping finished requests for waiting ones instantly.

The engine runs a simple schedule → forward → postprocess loop, splitting work into compute-bound prefill and memory-bound decode. Extras — chunked prefill, prefix caching, guided & speculative decoding, P/D disaggregation — squeeze out more speed. And it all scales across many GPUs and machines via tensor/pipeline/data parallelism.
