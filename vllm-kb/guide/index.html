Part 1 — The foundation

What an LLM actually does: predict the next word

A Large Language Model (LLM) — the thing behind ChatGPT, Claude, Gemini — has exactly one core skill: given some text, guess what comes next. That's it. Everything else is that one trick repeated very fast.

Step A — your words become tokens

Computers don't read English. So your sentence is chopped into small pieces called tokens (roughly word-fragments), and each token is swapped for a number — an ID — from the model's dictionary. This is tokenization.

tokenization
Hi, my name is
↓ tokenizer ↓
154111242756298

From here on, the model only ever sees numbers. A token's size in memory has nothing to do with how long the word is — "a" and "antidisestablishmentarianism" each become one (or a few) IDs.

Step B — it generates one token at a time

The model reads all your tokens, then predicts the single most likely next token. It appends that token to the text and repeats — reading everything again to predict the next one. This loop is called autoregression, and it stops when the model emits a special "I'm done" token.

autoregressive generation
prompt: 5 tokens

Notice the catch: to make each new token, the model re-reads the entire growing sequence. By token #500 it's re-reading 500 tokens every single step. That waste is exactly what vLLM is built to fix.

🧠 Mental modelAn LLM is an extremely well-read autocomplete. It doesn't "think ahead" — it commits to one token, then reconsiders everything to pick the next.
Part 2 — Why this is expensive

Everything happens on a GPU, and GPU memory is tiny & pricey

LLMs run on GPUs — specialized chips that do massive math in parallel. The scarce resource isn't speed, it's VRAM (the GPU's onboard memory). A model's whole world has to fit in VRAM, and VRAM is small and expensive.

How a GPU's memory gets divided up

Picture the VRAM as a plot of land. Several tenants must share it. Example: one NVIDIA A100 with 40 GB holding a 13-billion-parameter model.

The model weights and overhead are fixed. The only space we can manage cleverly is the KV cache — and how well we use it decides how many users we can serve at once.

Part 3 — The clever shortcut

The KV cache: don't redo work you've already done

Remember the waste from Part 1 — re-reading the whole sequence for every new token? Inside the model, "reading" a token means computing two things for it: a Key (K) and a Value (V). Crucially, a token's K and V never change once computed.

So the trick is obvious in hindsight: compute each token's K and V once, then save them. That saved store is the KV cache. Now generating a new token only needs to compute K/V for that one new token and reuse everything cached.

with vs without KV cache
❌ Without cache

Every step recomputes K/V for all tokens. Step 500 = 500 tokens of work.

→
✅ With KV cache

Step 500 computes K/V for just 1 new token, reuses 499 from cache.

Two phases fall out of this: prefill & decode

⚡ Prefill

Process all your prompt tokens at once to fill the KV cache and produce the first new token. Lots of math in parallel → compute-bound (limited by raw GPU horsepower).

🔁 Decode

Generate the rest, one token per step, reusing the cache. Little math, lots of memory shuffling → memory-bandwidth-bound (limited by how fast you can read memory).

🍳 AnalogyPrefill is prepping every ingredient before you start cooking (big upfront burst). Decode is plating one dish at a time, reusing the prep. Different bottlenecks — remember this; it explains almost every vLLM design choice later.
Part 4 — The problem vLLM was born to solve

The old way wasted most of the memory

Before vLLM, each request got one big contiguous (single unbroken) chunk of KV memory, sized for the maximum possible answer length — just in case. Almost no one uses the maximum. The rest is wasted. This is internal fragmentation.

internal fragmentation

A request reserves room for 2,048 tokens (256 MB) but only generates 100 tokens (12.5 MB):

used 12.5 MB
wasted 243.5 MB 😱

On a 12 GB KV budget at 256 MB each, you fit only ~40 requests on a GPU that could easily handle far more.

Smarter old systems guessed sizes by task type (chatbot=500, code=2048…). That created a new bug: free gaps that are big enough in total but not contiguous, so a new request won't fit. This is external fragmentation.

external fragmentation
free 500
in use (2048)
free 1000

1,500 tokens free in total, but a request needing 1,200 contiguous tokens → out-of-memory error, even though the space exists. Frustrating.

And a third miss: no sharing

Ask for "3 alternative answers" and the old way stored your prompt's KV three times — identical copies — because each answer lived in its own contiguous block. Wasteful, since the prompt never changes.

🎯 The three villainsInternal fragmentation (over-reserving), external fragmentation (unusable gaps), and no memory sharing. Keep them in mind — the next section defeats all three with one idea borrowed from operating systems.
Part 5 — The big idea

PagedAttention: steal the trick your laptop already uses

Your operating system solved this exact problem decades ago. Programs think they have one long continuous block of memory, but the OS secretly scatters it across small fixed-size pages in physical RAM, and a page table remembers where each page really lives.

📖 The mapping (memorize this line)In vLLM: blocks are pages · tokens are bytes · a request is a process. Everything else follows from this analogy.

KV memory is chopped into small fixed-size blocks

Instead of one giant reservation, the KV cache is split into many small blocks (16 tokens each, by default). A request grabs only as many blocks as it needs — and they can sit anywhere in physical VRAM. A lightweight page table (called the Block Manager) maps the request's neat logical order to the scattered physical blocks.

logical (what the request sees) → physical (reality)

Logical view — looks perfectly contiguous:

blk 0logical
blk 1logical
blk 2logical
↓ page table maps each one ↓

Physical VRAM — scattered, gaps reused by others:

#13someone else
#502→ blk 0
#105other chat
#12→ blk 1
#811→ blk 2

No giant contiguous reservation needed → external fragmentation gone. Blocks are tiny, so a near-empty last block wastes ≤15 tokens → internal fragmentation almost gone.

Sharing is now free: ref-counts

Three answers to the same prompt? They simply point to the same prompt blocks. vLLM keeps a reference count (ref_cnt) per block — "how many requests use me." Shared prompt blocks just bump the count instead of copying. Memory sharing → solved too.

Go deeper: how big is one block, really?

One block stores K and V for block_size tokens across every layer's attention heads. The size formula:

block_bytes = 2 (K&V) × block_size × num_kv_heads × head_dim × bytes_per_element

For Llama-3 8B in FP16, one token costs ~128 KB, so a default 16-token block ≈ 2 MB. If 8 GB of VRAM is left for KV cache, that's ~4,096 blocks to hand out. vLLM computes this number at startup and prints it as the available "GPU blocks."

Quick check: why are blocks made small (16 tokens) instead of huge?
Right idea: a small block means the only waste is in the final partly-filled block (≤15 tokens), and tiny blocks slot into any free gap — killing both kinds of fragmentation.
Part 6 — Serving many people at once

Continuous batching: never let the GPU sit idle

A GPU is happiest doing lots of work in parallel. So vLLM processes many requests together. The old "static batching" waited for the whole batch to finish before starting new work — so finished requests left their slots idle while slow ones ran on.

Part 8 — The clever extras

Five upgrades that make it even faster

Everything so far is the core. These features bolt on top. You don't need all the details — just the why behind each. Expand any card.

① Chunked prefill — don't let one long prompt hog the GPU

A 10,000-token prompt would monopolize a step and stall everyone else's decoding. Solution: split a long prompt into fixed-size chunks and prefill it across several steps, letting quick decodes interleave. Smoother for everyone — no single request blocks the line.

② Prefix caching — reuse work across different requests

If many requests share the same opening text (a long system prompt, a document), why recompute its KV every time? vLLM hashes each completed block of tokens (chaining in the previous block's hash, so the hash captures the whole prefix). A new request with the same prefix finds the hash, reuses those cached blocks (ref_cnt++), and skips straight to the new part. Huge win for chatbots and RAG.

③ Guided decoding — force valid output (e.g. always valid JSON)

Need the model to only ever output "Positive" or "Negative", or strict JSON? A finite state machine (a grammar) tracks which tokens are legal next. At each step, illegal tokens have their score set to -infinity via a bitmask — so they can never be picked. The model is gently railroaded into valid output.

④ Speculative decoding — guess ahead, verify in bulk

Decode is slow because it's one token at a time. Trick: a tiny, fast "draft" model guesses the next k tokens. The big model then checks all k guesses in a single pass. Correct guesses are kept for free; the first wrong one is rejected and corrected. Rejection sampling guarantees the output is identical to what the big model would have produced alone — just faster. vLLM supports n-gram, EAGLE, and Medusa style proposers.

⑤ Disaggregated P/D — put prefill and decode on different GPUs

Recall: prefill is compute-bound, decode is memory-bound — opposite appetites. So run them on separate machines, each tuned for its job. The prefill GPU computes the KV cache, then ships it over a fast connector (e.g. NIXL) to the decode GPU, which generates the answer. Each side scales independently.

Part 9 — When one GPU isn't enough

Scaling to many GPUs & many machines

Big models don't fit on one GPU, and big traffic needs many copies. Three ways to grow:

Tensor Parallelism (TP)

Split each layer's math across several GPUs in one machine. A driver broadcasts the work; all GPUs compute their shard together. Preferred inside a machine because GPUs there share fast links.

Pipeline Parallelism (PP)

Put different layers on different machines, like an assembly line. Used to span across machines when one box can't hold the model.

Data Parallelism (DP)

Run several full copies (replicas) of the engine; a coordinator load-balances users across them. This is how you serve more traffic.

Headless + API node

One node runs the public API server; other "headless" nodes just run engine replicas behind it. Clients only ever see the API node.

🏭 AnalogyTP = many workers building one car together. PP = an assembly line passing the car down. DP = many identical factories. Real deployments mix all three.
Part 10 — Measuring "fast"

Latency vs throughput, and the roofline

"Fast" means two different things, often in tension:

⏱️ Latency (one user's happiness)

TTFT — time to first token (how long until you see anything; set by prefill).

ITL / TPOT — time between tokens (how fast it "types"; set by decode).

E2E — total time for the full answer.

📊 Throughput (the operator's wallet)

Total tokens/second across all users. Bigger batches = more throughput, but each individual user may wait a touch longer. Goodput = throughput that still meets your latency promises.

The roofline: why bigger batches help — up to a point

This is the one chart that ties it together. The hill has two slopes: a rising "memory" wall and a flat "compute" ceiling.

roofline model
Decode sits on the blue slope — starved for memory bandwidth.

On the blue slope you're memory-bound (typical of decode) — the GPU's math units sit idle waiting for data. Pack more requests together (continuous batching!) and you climb right toward the red ceiling, finally using the GPU fully. That's why batching is the heart of vLLM.

The whole story in one breath

You now understand vLLM

An LLM predicts one token at a time, re-reading everything each step. To avoid that waste it saves each token's Key/Value in the KV cache. That cache is precious GPU memory, and the old way of storing it in big contiguous chunks wasted most of it (internal + external fragmentation) and couldn't share.

vLLM borrows the operating-system idea of paging: chop KV memory into small blocks, map them with a page table, and reference-count for sharing — that's PagedAttention. On top, continuous batching keeps the GPU busy by swapping finished requests for waiting ones instantly.

The engine runs a simple schedule → forward → postprocess loop, splitting work into compute-bound prefill and memory-bound decode. Extras — chunked prefill, prefix caching, guided & speculative decoding, P/D disaggregation — squeeze out more speed. And it all scales across many GPUs and machines via tensor/pipeline/data parallelism.
