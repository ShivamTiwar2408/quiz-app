Amazon VPC Reference Guide

AWS Networking, from the ground up

A clear, neutral reference to the building blocks of networking inside Amazon Web Services. Each entity is defined on its own terms, paired with a diagram, and placed in the larger picture. Every technical statement is drawn from official AWS documentation; sources are listed at the end.

§0 Overview & the mental model

Networking in AWS is organised around the Virtual Private Cloud (VPC) — a private, isolated network you define in the cloud. Everything else in this guide is something that lives inside a VPC, controls traffic within it, or connects it to the outside.

It helps to group the pieces into four layers:

  • The space — the VPC itself, its IP range (CIDR), and the subnets that divide it.
  • The steering — route tables decide where traffic goes; gateways (internet gateway, NAT gateway) are the exits.
  • The guards — security groups and network ACLs decide what traffic is allowed.
  • The interfaces — the elastic network interface (ENI) is the virtual network card every resource plugs into; VPC endpoints are private on-ramps to AWS services.
A useful first principle: a resource isn't "in" a VPC directly — its network interface (ENI) is. The ENI sits in one subnet, and that subnet's route table and the ENI's security groups govern everything the resource can reach. Keep this in mind; it makes the rest of the model click.

The master diagram — everything at once

§1 VPC — Virtual Private Cloud

VPC: a virtual network dedicated to your AWS account, logically isolated from all other virtual networks in the AWS Cloud. You define its IP range, add subnets, attach gateways, and associate security groups. — Amazon VPC User Guide

The VPC is the outermost boundary. Resources inside it can communicate with each other; nothing outside can reach in, and nothing inside can reach out, until you add a route and a gateway. This "closed by default" posture is the foundation of VPC security — every path to the outside world is something you explicitly create.

A VPC is scoped to a single AWS Region, but it spans all the Availability Zones (AZs) in that Region — so you can place resources across physically separate datacentres for resilience while staying in one network.

Analogy: a VPC is like leasing a private, fenced-off floor in a large building. AWS owns the building and the street outside; your floor is yours alone, and you decide where to cut doors.

§2 CIDR & IP addressing

When you create a VPC you give it an IP range in CIDR notation (Classless Inter-Domain Routing), such as 10.0.0.0/16. Subnets then carve smaller ranges out of it.

CIDR writes a range as address/prefix. The prefix is the number of fixed leading bits; the remaining bits are free and define how many addresses the block contains. A smaller prefix means a larger block.

CIDRFixed bitsApprox. addressesTypical use
10.0.0.0/161665,536An entire VPC

0.0.0.0/00all addresses"Any destination" — the default route
Remember 0.0.0.0/0. It means "everything / anywhere". As a route destination it's the catch-all that points at the internet, and you'll see it again in route tables, the internet gateway, and the NAT gateway.

§3 Subnets

Subnet: a range of IP addresses within a VPC. You launch AWS resources into subnets. Each subnet resides in exactly one Availability Zone.

Subnets partition the VPC's address space and let you separate tiers of an application — for example, public-facing web servers in one subnet and databases in another. AWS itself recommends putting resources that shouldn't be reachable from the internet into private subnets.

Public vs private — the defining rule

There is no "public" checkbox. A subnet is public only because its route table sends internet-bound traffic (0.0.0.0/0) to an internet gateway. A subnet with no such route is private. The construct is identical — the route table is what makes the difference.

§4 Private & public IP addresses

Every network interface in a VPC has a private IPv4 address drawn from its subnet's range (e.g. 10.0.1.42). Private addresses are routable only inside the VPC and any networks privately connected to it.

A public IPv4 address is globally routable from the internet. A resource only has one if it's assigned — either auto-assigned (a subnet attribute) or via an Elastic IP address, a static public IP you allocate and can move between resources.

Analogy: a private IP is a desk extension — only diallable from inside the building. A public IP is a public phone number the outside world can call. Many private desks can share one public number through an operator (NAT, §7).
Key fact: by default a resource in a custom (non-default) subnet gets a private IP but no public IP. Without a public IP — or a NAT in the path — it cannot exchange traffic with the internet directly. This is central to how the internet gateway and NAT gateway differ (§6–§7).

§5 Route tables

Route table: a set of rules ("routes") that determine where network traffic from a subnet is directed. Each subnet is associated with exactly one route table.

Every route has a destination (a CIDR range) and a target (where to send traffic for that range). Common targets: local (within the VPC), an internet gateway, a NAT gateway, a VPC endpoint, a peering connection, or a transit/virtual private gateway.

DestinationTargetMeaning
10.0.0.0/16localTraffic within the VPC stays local (always present)
0.0.0.0/0igw-…Everything else → the internet (makes the subnet public)
0.0.0.0/0nat-…Everything else → a NAT gateway (private subnet egress)
pl-… (S3)vpce-…S3 traffic → a gateway endpoint

The golden rule: longest-prefix match wins

When a packet's destination matches more than one route, the router uses the most specific route — the one with the longest prefix (largest /n). This single rule is why a VPC endpoint can divert S3 traffic away from a NAT gateway: a service prefix-list route is more specific than the catch-all 0.0.0.0/0.

§6 Internet gateway (IGW)

Internet gateway: a horizontally-scaled, redundant VPC component that enables communication between resources in your VPC and the internet. One IGW is attached per VPC.

It does two things: it serves as the target for internet-bound routes (0.0.0.0/0), and it performs one-to-one NAT between a resource's private IP and its public IP. Traffic flows both ways — the IGW supports inbound connections to resources that have a public address (e.g. a public web server).

Hard requirement: the internet gateway only routes for a resource that has a public IP address, because it maps private↔public one-to-one. A resource with only a private IP has nothing to map to, so its internet-bound packets are dropped. This is precisely the gap the NAT gateway fills.

§7 NAT gateway

NAT gateway: a Network Address Translation service that lets resources in a private subnet connect outbound to services outside the VPC, while preventing the outside from initiating connections inbound.

A public NAT gateway is placed in a public subnet and is given an Elastic IP. The path for a private resource reaching the internet is:

  1. The resource sends a packet outward; its route table says 0.0.0.0/0 → NAT gateway.
  2. The NAT gateway rewrites the packet's source to its own address.
  3. It forwards to the internet gateway, which maps the NAT's address to its Elastic (public) IP.
  4. Replies return to the Elastic IP → NAT → translated back to the original private resource.

Because connections must originate inside the VPC, the NAT gateway gives private resources outbound reach without exposing them to unsolicited inbound traffic. (A private NAT gateway variant routes to other VPCs or on-premises networks via a transit/virtual private gateway, with no Elastic IP and no internet.)

Analogy: the NAT gateway is the building's front-desk operator. Staff can dial out, but every outgoing call shows the building's one public number, and the outside world can only ever call that number back — never a private desk directly. The operator only connects calls that began inside.
Two cost meters. A NAT gateway bills on an hourly rate (for existing) plus a per-GB data-processing rate (for traffic through it). The hourly part is fixed; the per-GB part scales with volume — which is what gateway endpoints (§11a) can offload.

§8 Security groups

Security group: a virtual firewall that controls inbound and outbound traffic at the level of an individual resource's network interface. It is stateful and supports allow rules only.
  • Stateful: if you allow a request out, the corresponding reply is automatically allowed back in — you don't write a return rule.
  • Allow-only: there are no deny rules. Anything not explicitly allowed is denied.
  • All rules evaluated: the security group considers all of its rules before deciding to permit traffic. Rules can reference other security groups, not just IP ranges.
Analogy: a bouncer with a guest list who also has a good memory — only listed names get in, and anyone they let out is allowed back without re-checking.

§9 Network ACLs

Network ACL (NACL): an optional, stateless firewall that controls traffic at the subnet level, supporting both allow and deny rules evaluated in number order.

Where a security group wraps a single resource, a network ACL wraps an entire subnet — acting as a coarse, secondary guard rail. AWS guidance: use security groups as the primary control, and add NACLs for defence-in-depth (e.g. to deny a specific range, or to protect a subnet even if a resource is launched with the wrong security group).

§10 Elastic network interface (ENI)

Elastic network interface: a logical networking component in a VPC that represents a virtual network card. Its attributes follow it as it is attached to, detached from, and reattached to instances. (In the console & EC2 API it's simply called a "network interface".)

The ENI is the component that is actually "in" a subnet. Compute attaches to it; the ENI provides the resource's presence on the network. According to AWS, an ENI can carry:

  • A primary private IPv4 address (and optional secondary private IPv4s), from the subnet's range.
  • IPv6 addresses (if the subnet has an IPv6 range).
  • One Elastic IP per private IPv4, and one public IPv4.
  • A MAC address.
  • One or more security groups.
  • A source/destination check flag (disabled for NAT/router/firewall appliances).

An ENI is bound to one subnet (hence one Availability Zone). Each instance has a primary network interface that can't be detached; you can add secondary ENIs and even move them — with their IPs and security groups — to another instance, redirecting traffic. Some ENIs are requester-managed: created and operated by AWS services on your behalf (interface endpoints and many managed services use these).

Why this matters: because reachability is a property of the ENI's subnet and security groups, "moving a resource onto a network" really means "placing its ENI in a subnet". Routing, IP type, and firewall rules all follow from where that interface sits.

§11 VPC endpoints

VPC endpoint: a way to connect resources in your VPC to AWS services (and some third-party / cross-account resources) privately — over the AWS network, without an internet gateway or NAT device.

Endpoints keep service traffic off the public internet, which improves security and can cut NAT data-processing costs. There are two main types for reaching AWS services, and they work very differently. The next two sub-sections cover each.

§11a Gateway endpoint

Gateway endpoint: a VPC endpoint that targets Amazon S3 or DynamoDB — and only those two services. It is implemented as a route-table entry, not an interface, and there is no charge for it. Gateway endpoints do not use AWS PrivateLink.

You add a gateway endpoint to one or more route tables. AWS installs a route whose destination is the service's managed prefix list (e.g. pl-xxxx — the set of IP ranges S3 or DynamoDB uses in the Region) and whose target is the endpoint. Traffic to the service then matches that route — and, by longest-prefix match (§5), takes the endpoint instead of a NAT or internet gateway, riding the AWS backbone directly.

  • Services: S3 and DynamoDB only.
  • Mechanism: a route to a prefix list — no ENI, no private IP.
  • Cost: free (no hourly fee, no data-processing fee).
  • Reach: only from within the VPC it's attached to (a route table is local to its VPC).

§11b Interface endpoint (AWS PrivateLink)

Interface endpoint: a VPC endpoint powered by AWS PrivateLink that is implemented as an elastic network interface with a private IP placed in your subnet. It supports most AWS services (and partner / cross-account services) — for example Bedrock, ECR, CloudWatch Logs, SQS, KMS, Secrets Manager.

For each subnet you choose, AWS creates an endpoint network interface (a requester-managed ENI) with a private IP. With private DNS enabled, the service's normal DNS name resolves to that private IP inside your VPC, so existing SDK/API calls transparently use the endpoint. Traffic stays on the AWS network and never traverses the public internet.

  • Services: most AWS services and PrivateLink-enabled third-party/partner services.
  • Mechanism: an ENI with a private IP in your subnet; resolved by DNS.
  • Cost: an hourly charge per endpoint (per AZ) plus a per-GB data-processing charge.
  • Reach: works from the VPC and, unlike gateway endpoints, over VPN, Direct Connect, peering, and across accounts.
Why two types exist: gateway endpoints were AWS's first design, built for the two highest-volume services (S3, DynamoDB) as a free, route-based shortcut. Interface endpoints / PrivateLink are the general successor — they work across more connectivity scenarios (VPN, Direct Connect, peering, cross-account), which a local route table cannot. Every service introduced since uses the interface model.

§12 How it fits together

A request leaving a resource in a VPC is shaped by these components in sequence:

  1. The resource sends traffic through its ENI (§10), which sits in a subnet (§3).
  2. The ENI's security group (§8) must allow the traffic; the subnet's network ACL (§9) may also filter it.
  3. The subnet's route table (§5) selects a target by longest-prefix match:
    • destined for the VPC → local;
    • destined for S3/DynamoDB with a gateway endpoint (§11a) → the AWS backbone, free;
    • destined for another service with an interface endpoint (§11b) → its private-IP ENI;
    • destined for the internet from a public resource → the internet gateway (§6);
    • destined for the internet from a private resource → the NAT gateway (§7) → internet gateway.
