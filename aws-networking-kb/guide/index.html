Part 0 — The thread we'll follow

One concrete question pulls the whole map together

Abstract networking is hard to remember. So we'll hang every concept on a single real scenario:

🧵 The running exampleYou have an AWS Lambda function that calls services like Amazon Bedrock, S3, and DynamoDB. Today it just works. Now you need it to also reach a resource that lives only inside a private network. So you "put the Lambda in a VPC" — and suddenly its calls to Bedrock and S3 start timing out. Why?

Answering that "why" requires understanding the VPC, its subnets, how IP addresses and route tables steer traffic, the difference between an internet gateway and a NAT gateway, what a security group does, and — the star of the show — the ENI, the virtual network card that is the actual thing that "lives inside" a network. By the end you'll be able to draw the before/after yourself.

📚 SourcesEvery fact here is drawn from the official AWS documentation: the Amazon VPC User Guide ("How Amazon VPC works", NAT gateways), the AWS PrivateLink guide (VPC endpoints), and the AWS Lambda Developer Guide (VPC networking & Hyperplane ENIs). Links are in the recap.

Part 1 — The container

The VPC: your own private slice of the cloud network

A VPC (Virtual Private Cloud) is, in AWS's own words, "a virtual network dedicated to your AWS account, logically isolated from other virtual networks in the AWS Cloud." It is the outermost box that everything else lives inside.

When you create one, you give it an IP address range using CIDR notation — for example 10.0.0.0/16. That range is the pool of private addresses every resource inside the VPC will draw from.

🏢 AnalogyA VPC is like leasing a private floor in a giant office building. AWS owns the building and the public street outside; your floor is fenced off from every other tenant. 10.0.0.0/16 is the range of desk numbers you're allowed to assign on your floor.

CIDR in one minute

CIDR (Classless Inter-Domain Routing) writes an IP range as address/prefix. The number after the slash says how many leading bits are fixed — the rest are free to vary, and those define the size of the range.

CIDRFixed bitsAddressesMeaning
10.0.0.0/1616~65,536A whole VPC
10.0.1.0/2424256One subnet inside it
0.0.0.0/00everything"any destination" — the default route (remember this one!)

Smaller prefix = bigger range. /16 is huge; /24 is a neighbourhood; /32 is a single address.

a VPC is the outer boundary — nothing inside it is reachable from outside by default
VPC boundaryno connectivity by default

A brand-new custom VPC is sealed. Resources inside can talk to each other, but there is no path to the internet or to other networks until you add one. That "sealed by default" property is the whole point — you opt into every connection.

Part 2 — Dividing the space

Subnets: rooms within your floor

A subnet is "a range of IP addresses in your VPC" — a slice of the VPC's CIDR. You launch resources (EC2 instances, ENIs, etc.) into subnets, not directly into the VPC. Each subnet lives in exactly one Availability Zone (a physically separate datacentre), which is how you spread across AZs for resilience.

🚪 AnalogyIf the VPC is your office floor, subnets are the individual rooms. Each room holds a block of desk numbers (10.0.1.0/24), and each room is in a specific part of the building (an Availability Zone).

The crucial distinction: public vs private subnet

Here's the single most important — and most misunderstood — fact in AWS networking:

💡 A subnet is "public" or "private" purely because of its route tableThere is no checkbox that makes a subnet public. A subnet is public if its route table sends internet-bound traffic (0.0.0.0/0) to an internet gateway. It is private if it has no such route. Same subnet construct — the routing decides the label.

one VPC, two subnets in two AZs — identical except for where their routes point

Hold this thought — it's the key that unlocks the Lambda mystery later. We'll define route tables and the internet gateway in the next two parts, then this picture will be fully legible.

Part 3 — Addresses

Private vs public IP addresses

Every networked resource needs an address. In a VPC there are two kinds, and the difference matters enormously.

🏠 Private IP

Drawn from the subnet's CIDR (e.g. 10.0.1.42). Only routable inside the VPC and connected private networks. Every resource gets one. The internet cannot reach a private IP directly.

🌍 Public IP

A globally-routable address reachable from the internet. A resource only gets one if it's explicitly assigned (auto-assigned in a public subnet, or via an Elastic IP — a static public IP you own).

📮 AnalogyA private IP is your desk extension number — only dialable from inside the building. A public IP is the building's public phone number the outside world can call. Many desks can share one public number through the front-desk operator (that operator is NAT — coming up in Part 6).

⚠️ The fact that breaks intuitions laterAWS says: by default an instance in a non-default subnet "has a private IPv4 address, but no public IPv4 address." And critically — a VPC-attached Lambda function never gets a public IP at all, even in a public subnet. Keep this; it's why "just use a public subnet" does not fix the Lambda. We'll prove it in Part 9.

Part 4 — The steering logic

Route tables: the signposts that decide where packets go

AWS defines a route table as "a set of rules, called routes, that determine where network traffic from your VPC is directed." Each subnet is associated with exactly one route table. Every route has two parts:

  • Destination — a CIDR range of where the traffic is headed (e.g. 10.0.0.0/16, or 0.0.0.0/0 for "anywhere").
  • Target — the gateway, interface, or connection to send that traffic through (e.g. local, an internet gateway, a NAT gateway, an endpoint).
🗺️ AnalogyA route table is the set of road signs at an intersection: "Local addresses → straight ahead", "Everywhere else → take the highway ramp". The packet reads the signs and turns accordingly.

The golden rule: longest-prefix match wins

When a packet could match more than one route, the router picks the most specific one — the route with the longest prefix (the biggest /number). This one rule explains how VPC endpoints later "steal" traffic away from the NAT. Try it:

🔑 Why this mattersThe DynamoDB route (/20, 20 fixed bits) is more specific than the catch-all 0.0.0.0/0 (/0). So DynamoDB traffic takes the Gateway Endpoint and never touches the NAT — even though both routes technically match. That's longest-prefix match doing real work.

Part 5 — The door to the internet

The Internet Gateway (IGW): the only public doorway

An internet gateway is a component you attach to your VPC that "enables your instances to connect to the internet through the Amazon EC2 network edge." It does two jobs: it provides a target for internet-bound routes, and it performs 1:1 NAT between a resource's private IP and its public IP.

⚠️ The IGW has a hard requirementThe internet gateway will only route traffic for a resource that has a public IP address. It maps private↔public one-to-one. If a resource has only a private IP, the IGW has nothing to translate to — so it drops the packet. This single rule is the reason a NAT gateway has to exist.

the IGW only works for resources that own a public IP
has public IP → reaches internetprivate only → IGW drops it

So an IGW alone is not enough for private resources. Something must give the private resource a public face. That something is the NAT gateway.

Part 6 — Outbound-only internet for private resources

The NAT Gateway: a one-way valve to the internet

AWS defines it precisely: a NAT gateway lets "instances in a private subnet connect to services outside your VPC, but external services can't initiate a connection with those instances." It is outbound-only — perfect for a backend that needs to call APIs but must never accept unsolicited inbound traffic.

How it actually works

A public NAT gateway sits in a public subnet and owns an Elastic IP (a static public address). The flow, per AWS:

  1. The private resource sends a packet to the internet. Its route table says 0.0.0.0/0 → NAT gateway.
  2. The NAT gateway rewrites the source from the resource's private IP to the NAT's own private IP.
  3. It forwards to the internet gateway, which maps the NAT's private IP to its Elastic (public) IP.
  4. Replies come back to the Elastic IP → NAT → translated back to the original private resource.
🛎️ AnalogyThe NAT gateway is the building's front-desk operator. Staff (private resources) can dial out, but every outgoing call shows the building's public number. The outside world can only ever call that one number back — it can never directly ring a private desk. And the operator only connects calls that started inside.

private resource → NAT (in public subnet) → IGW → internet
💸 Two separate costs (this matters in Part 10)A NAT gateway bills you on two independent meters: an hourly charge just for existing, plus a per-GB data-processing charge on every byte that flows through it. The hourly fee is fixed; the per-GB fee scales with traffic. Remember this — it's exactly what VPC endpoints optimise.

Part 7 — The firewall

Security Groups: a stateful firewall around each resource

Route tables decide where a packet can go. A security group decides whether it's allowed at all. It's a virtual firewall attached to a resource's network interface, with separate inbound and outbound rules.

Two defining properties:

  • Allow-only. Rules only permit traffic — there are no "deny" rules. Anything not explicitly allowed is implicitly denied.
  • Stateful. If you allow a request out, the reply is automatically allowed back in (and vice-versa). You don't write a return rule.
🛡️ AnalogyA security group is a bouncer with a guest list. Only names on the list get in. And it remembers: if it let someone out to grab something from their car, it lets them back in without rechecking the list. (Contrast: a Network ACL is the building's perimeter gate — stateless, and operates per-subnet rather than per-resource.)

stateful: outbound 443 allowed ⇒ the response is allowed back automatically

For most setups, allowAllOutbound on the resource's security group plus a rule on the destination (e.g. an endpoint) permitting inbound 443 from it is all you need.

Part 8 — The star of the show

The ENI: the virtual network card that actually "lives in" the subnet

This is the concept that makes everything else click. An ENI (Elastic Network Interface) is a virtual network card. Exactly as a physical server has a physical NIC that plugs into a switch and gives it a presence on the network, an ENI is the software equivalent for cloud compute.

What an ENI carries

An ENI bundles together everything needed to be "on the network":

anatomy of an ENI
🧠 The mental model that unlocks AWS networkingWhen people say "the Lambda is in the VPC," what is literally in the VPC is an ENI sitting in a subnet. The compute itself lives elsewhere and reaches the network through that ENI. So the ENI's subnet → its route table → its security group together decide everything the attached compute can and cannot reach.

🔌 AnalogyThe ENI is the network port on the wall plus the cable plugged into it. Your computer (compute) can be anywhere, but the moment its cable plugs into a specific wall port, it inherits that room's address range, that room's signs (route table), and that room's door policy (security group). Move the cable to a different room and everything about its connectivity changes — even though the computer didn't move.

Part 9 — How Lambda plugs in

Hyperplane ENIs and the Lambda mystery, solved

Now we can answer the question from Part 0. First, two facts straight from the AWS Lambda docs:

  • Every Lambda already runs in a VPC — one that is "owned and managed by the Lambda service," invisible to you, with internet access. That's why an un-configured Lambda can call Bedrock/S3/DynamoDB freely.
  • When you attach a Lambda to your VPC, Lambda creates a Hyperplane ENI — a special managed ENI — inside your chosen subnet. "By default, Lambda functions have access to the public internet. When you attach your function to a VPC, it can only access resources available within that VPC."

What a Hyperplane ENI is

An ordinary VPC would create one ENI per resource. Lambda is massively concurrent, so it uses Hyperplane ENIs: one shared ENI is created per unique (subnet × security group) combination, and reused across thousands of concurrent executions. Each supports up to ~65,000 connections; Lambda scales them automatically. This is why VPC Lambdas no longer suffer the old multi-second cold-start penalty — the ENI is set up ahead of time and shared, not built per-invocation.

🎯 The "just use a public subnet" trap — debunkedThe AWS docs state it flatly: "Connecting a function to a public subnet doesn't give it internet access or a public IP address." A VPC Lambda's Hyperplane ENI only ever gets a private IP. And from Part 5, the IGW drops anything without a public IP. So a Lambda in a public subnet still cannot reach the internet. It must sit in a private subnet and egress via a NAT gateway (or via VPC endpoints).

So, why did Bedrock and S3 start timing out?

Before: the Lambda lived in the AWS-managed Lambda network, which has a built-in public path. Bedrock, S3, DynamoDB, ECR — all reachable for free, zero config.

After attaching your VPC: the Lambda's traffic now flows through a Hyperplane ENI in your private subnet. That subnet has no route to the internet. So unless you add a NAT gateway (or endpoints), every call to a public AWS endpoint has nowhere to go — and hangs until it times out. The container image pull from ECR can even fail at cold start, so the function never boots.

The fix is exactly the plumbing we've been building: a NAT gateway to restore outbound internet for the public AWS APIs, and — for the resource that lives only inside a network — a VPC endpoint. Which brings us to the last piece.

A VPC-attached Lambda in a public subnet still can't reach the internet. Why?
Correct: the Hyperplane ENI never receives a public IP, and the internet gateway only routes for resources that have one. No public IP ⇒ IGW drops the packet ⇒ no internet, regardless of subnet label. You need a NAT gateway in a private-subnet setup.
Part 10 — Private doorways to AWS services

VPC Endpoints: reach AWS services without the public internet

A VPC endpoint lets resources in your VPC reach AWS services over the AWS private network — no internet, no NAT. There are two flavours, and the distinction is exam-and-bill critical.

Gateway Endpoint

S3 and DynamoDB only — these are the only two services that support it. It is not an ENI: it's a route-table entry pointing at a managed prefix list. Traffic to S3/DynamoDB matches that specific route (longest-prefix match!) and goes straight to the AWS backbone. Free — no hourly fee, no data charge.

Interface Endpoint (PrivateLink)

Almost every other service (Bedrock, ECR, CloudWatch Logs, SQS, KMS…). It is an ENI with a private IP placed in your subnet. With private DNS enabled, the service's normal hostname resolves to that private IP. Costs an hourly fee + per-GB, per AZ.

📌 Why only S3 & DynamoDB get the free gatewayGateway endpoints were AWS's first-generation design (built for the two highest-volume, most universal services). PrivateLink interface endpoints are the general-purpose successor — they work across VPN, Direct Connect, peering, and cross-account, which route-table-based gateway endpoints cannot. Every service launched since uses the interface model. So Bedrock doesn't "lack" a feature — S3/DynamoDB are the special exceptions.

gateway endpoint = a route (free) · interface endpoint = an ENI in your subnet (paid)
💡 Back to "what do endpoints achieve if I keep the NAT?"You keep the NAT for Bedrock/ECR/Logs, yes. But adding the free S3 + DynamoDB gateway endpoints diverts your highest-volume traffic off the NAT's per-GB meter (the hourly fee is sunk either way). You also shrink the blast radius — your data stores stay reachable even if the NAT is unhealthy. Near-zero effort, can only help.

You add an S3 Gateway Endpoint but keep a NAT gateway for Bedrock. What changes for S3 traffic?
Correct: longest-prefix match sends S3 traffic to the gateway endpoint (its prefix-list route is more specific than 0.0.0.0/0 → NAT). It rides the AWS backbone for free, off the NAT's per-GB meter. Gateway endpoints have no hourly or data charge.

The one sentence to remember

🧭 North star"Putting compute in a VPC" means placing an ENI in a subnet — and from that moment the subnet's route table (where it can go), its IP type (public vs private), and its security group (what's allowed) govern everything. Reachability you got for free outside the VPC must now be rebuilt with a NAT gateway and/or VPC endpoints.
